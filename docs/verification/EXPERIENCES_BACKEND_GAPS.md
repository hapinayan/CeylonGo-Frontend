# Experiences backend gaps

Audit revision: `f795562e352a48c6d7cf9a6d5ffa2265352797ec`, branch `feature/tr05-backend-local-complete`. Source inspection only. The endpoints and fields in the **Proposal** column are design proposals.

## Existing public boundary

The general Activities module exposes public slots for a known activity ID. Its management endpoints require provider or admin authorization. The Eco-Tourism module exposes its own public browse, taxonomy, details, reviews, and availability contracts. Community listings can reference activities, but those references do not establish a general Activities catalog API. The shared publication predicates require an approved, eligible provider and enforce the appropriate activity or Eco listing state.

## Verification dependencies

Live acceptance requires an authorized local backend and a safe data configuration with public test listings. For weather smoke tests, use a controlled upstream stub and exercise missing credentials, rate limiting, stale responses, and cross-origin visibility of `Retry-After`. Booking, wishlist mutations, and payments are outside this audit.


## Traveler workflow gaps and acceptance

The following contracts were verified in source and integrated only for Eco-Tourism. Booking, cancellation and payment acceptance still require the gates in [external acceptance](EXPERIENCES_EXTERNAL_ACCEPTANCE.md).

| Area | Verified behavior | Open decision and acceptance |
|---|---|---|
| General Activities wishlist | `app/routers/wishlists.py` exposes traveler-owned Eco wishlist operations. No public general Activity wishlist resource was found. Eco list uses server totals, and unavailable rows may have a null public projection. | Define Activity and Eco identity and whether saved experiences use a unified resource. Verify ownership, visibility, duplicate handling, and stable pagination. Verify provider suspension behavior in the existing Eco available-only filter. |
| Reservation writes | `app/routers/eco_reservations.py` and `app/services/eco_reservations.py` enforce group bounds, safety, minimum age, capacity, duplicate held reservations, eligibility and authoritative totals. There is no client idempotency key. Optional native maximum-age records can affect acceptance without a corresponding public detail field. | Decide how to expose public maximum age and an idempotent reservation or reconciliation contract. Verify timeout, duplicate and concurrency scenarios. An uncertain client result is never automatically retried. |
| Booking list and cancellation | My Eco reservations returns a page array with no total metadata and includes the experience ID, not a title or host projection. Owner-only detail returns the same 404 for unowned and missing rows. Ordinary cancellation checks status, start time, unpaid status and saved policy snapshots. The response lacks an explicit cancellation-eligibility projection. | Decide whether to expose totals, safe listing summaries, and server eligibility flags. Verify free-window boundaries, paid cancellation and refunds separately. |
| Payment checkout and reconciliation | The native Eco status and initiation endpoints are registered. Initiation requires server-side activation and an eligible confirmed, unpaid, future booking. The server supplies signed checkout parameters; the webhook and ledger provide authoritative capture and refund state. | Approve sandbox use, callback routing, public activation and return/status behavior. Verify tampering, retry eligibility, expiry, late capture, duplicate callbacks and refunds. Checkout stays unavailable in the UI. |
